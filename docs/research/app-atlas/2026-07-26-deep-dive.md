## Headline: the Audi US/CA login root cause (#13)

It was never a missing `client_secret`. It was the wrong endpoint. Same client
id and body in every case:

| grant | `identity.na.vwgroup.io/oidc/v1/token` | `na.bff.cariad.digital/auth/v1/idk/oidc/token` |
|---|---|---|
| `authorization_code` | `401 invalid_client` "missing client_secret for clientId 7c6b4634-…" | `400 Bad Request` (client accepted, code rejected) |
| `device_code` | `400 expired_token` (client accepted) | `400 expired_token` (client accepted) |

The IDP demands client authentication for the `authorization_code` grant only.
Audi's IDK is a public PKCE client with no secret to offer, which is precisely
the reported symptom, and it explains why the QR/device-grant path always worked
while email and password never did. Shipped in v2.24.0; the two flows now use
different endpoints on purpose.

`na.bff.cariad.digital` has **zero DEX hits**, exactly like the NA client id
itself. Both arrive at runtime from the US market config, so absence from the
APK proves nothing here. Do not "correct" this back on DEX-absence grounds.

Still live-gated: `400` proves the client is accepted, not that a real code
completes end to end.

## Correction: X-QMAuth is not in the myAudi APK

`grep -aic qmauth` over all 16 DEX files of myAudi 5.6.0 returns **0**, and the
same holds for all seven cached brand string dumps. Earlier notes claiming the
myAudi US DEX evidences X-QMAuth are wrong.

What myAudi 5.6.0 actually ships, contiguous in the string pool:
`X-Assertion, X-Android-Package-Name, X-Platform, X-Client-ID, X-App-Name,
X-App-Version, X-Device-ID, X-SecurityToken, X-RequestUuid, X-API-Version`.

Our `_calculate_x_qmauth` remains a faithful port of the evcc implementation and
is not being changed, but the APK is not its evidence.

## VW North America: the app never logs in, and con-veh is a proxy

`grep -ac vwgroup` returns **0** across all three myVW DEX files. There is no
`signin-service`, `_csrf`, `relayState` or `login/identifier` string anywhere in
the app. It opens a CustomTab and lets the browser handle credentials.

**Consequence:** the myVW APK can never tell us which form field our headless
scrape is missing, because the app never submits that form. Any future analysis
that tries to answer a login question from this APK is looking in the wrong place.

Live-probed chain: our authorize call to `b-h-s.spr.us00.p.con-veh.net` returns
`302` to `identity.na.vwgroup.io/oidc/v1/authorize` carrying **con-veh's own**
client `b680e751-…@apps_vw-dilab_com`, scope `openid email`, its own state and
callback, plus `ui_locales=en-US`. Our `code_challenge` is not forwarded inward,
so the PKCE pair only matters for the outer con-veh token call.

Also proven: the NA sign-in service answers **HTTP 500 for a client id it cannot
resolve** (`59992128-…_MYVW_ANDROID` → 500, `b680e751-…` → 400). v2.24.0 now
reads the client id out of the URL we land on rather than assuming it.

Other deltas worth knowing: the app sends nine `x-app-*` / `x-user-*` headers we
do not, sends neither `nonce` nor `code_challenge_method` (both zero hits) while
we send both, and carries Play Automatic Integrity Protection (`com.pairip.*`)
with an AZS layer. The AZS HTTP paths in the DEX are third-party account linking
only, so there is no evidence the main login is Play-Integrity-gated.

`b-h-s.spr.ca00.p.con-veh.net` does resolve in DNS but rejects the MYVW client on
authorize with `400`, while `us00` gives `302`. Routing CA through us00 is
therefore correct, though the older "ca00 has zero hits" justification was a
DEX-only statement, not a network fact.

## Known metadata error: Porsche version

The cache and the generated pages record `12.24.27` from apkmirror. The APK we
actually hold reports **`20.26.28-pcna`** in its binary AndroidManifest ("pcna" =
Porsche Cars North America). Either the Play catalogue served an NA-variant build
or apkmirror tracks a different lineage. Do not treat `12.24.27` as the current
Porsche build without re-checking. This is not fixed in the cache because the
watcher owns that file and would overwrite it.

## The download route that actually works

`scripts/app_atlas/build_atlas.py` as committed has **no apkeep integration**.
Its chain is APKCombo then Uptodown, which is stale for the gated apps and then
runs into apktool being far too slow on 100 MB+ packages. The route that works:

```bash
# a FRESH anonymous Play credential per app (they are session and rate limited)
curl -s -A com.aurora.store https://auroraoss.com/api/auth   # -> {"email":…,"auth":"ya29…"}

~/.local/bin/apkeep.exe -a <package> -d google-play \
  -e <email> --auth-token <ya29-token> --accept-tos <dest-dir>
```

The token goes in `--auth-token`, **not** `--aas-token`; that mistake is what
makes it fall back to mirrors and decoys. `apkeep.exe` is already PE-stack
patched. Fallbacks in order: APKCombo (this is how VW 4.2.1 was obtained), then
Uptodown (which serves a decoy `com.uptodown.*` installer for gated apps, so
always verify the package name in the binary AndroidManifest), then APKMirror.

Analysis: `unzip -q <apk> 'classes*.dex'` and grep the raw DEX with `grep -a`.
Do not run apktool. Always read the version out of the binary AndroidManifest
rather than trusting a filename.
